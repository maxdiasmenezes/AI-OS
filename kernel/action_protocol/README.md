# Action Protocol

Milestone 39: the reliable, machine-readable protocol through which a
model can return exactly one validated decision - without ever generating
or altering a tool name, a resource key, or an arguments object itself.

## Two-stage architecture

**Stage A - deterministic candidate resolution** (`candidates.py`).
`resolve_action_candidates()` inspects the raw user request against a
small, conservative, hand-written grammar over the six actions
`kernel/tools/registry.py`'s `ActionRegistry` knows about, resolves any
named target against the real `ToolsConfig` (exact, case-insensitive
symbolic keys only - no aliases, no fuzzy or semantic matching, no
default target), and returns a `CandidateResolution`: either a
deterministic `RequestClarificationDecision` (a supported single-action
intent was recognized but its required target is missing - the model is
never called for this) or zero or more immutable `ActionCandidate`
objects. This stage never calls a model and never executes anything.

**Stage B - constrained model decision** (`prompt.py` + `parser.py`).
`build_prompt()`/`build_schema()` give the model the request text, a short
code-generated description of each candidate (an opaque `candidate_id`,
a plain-language summary, and whether it is sensitive - never a raw path,
command, or executable), and a JSON Schema that structurally permits only
`respond`, `select_candidate`, `request_clarification`, or
`cannot_complete`. When there are zero candidates, `select_candidate` is
entirely absent from the schema - the model is structurally unable to
select a tool, not merely instructed not to. `parse_decision()` then
strictly parses the model's complete response and, for
`select_candidate`, resolves `candidate_id` back to the *exact* immutable
`ActionCandidate` object that was offered - never reconstructing tool
name or arguments from model text.

## Deterministic, immutable candidates

An `ActionCandidate` carries a code-generated, opaque, request-local
`candidate_id` (`"candidate_1"`, `"candidate_2"`, ...) that is never
derived from the action name or resource key, a `kernel.tools.types.
ActionRequest` (the real action + resource key, entirely code-owned), a
`sensitive` flag sourced from `ActionRegistry`, and a `user_summary`
generated by code from registry metadata only. The model receives the
`candidate_id` and `user_summary` and nothing else about a candidate; it
never sees or produces `tool_name`, `resource_key`, or an `arguments`
object.

## Exact symbolic resource resolution

Target text extracted from the request is validated against a narrow
shape grammar (`[A-Za-z0-9_-]`, 1-64 characters) *before* it is ever
looked up - a destructive command, a drive-letter path, or a quoted shell
fragment can never survive that shape check to reach a registry lookup.
A syntactically valid target that is not an actual configured key produces
**zero candidates**, never a guess. There is no alias or display-name
mechanism, matching the real `kernel/config/tools.yaml` schema exactly.

## Dynamic candidate-ID schema

One JSON Schema is generated per request. `protocol_version` is
`const: 1`; every branch sets `additionalProperties: false` and an exact
`decision` constant. `select_candidate.candidate_id` is an `enum`
containing exactly the request's live candidate IDs - never an open
string. The parser re-validates everything the schema already constrains
(unknown candidate IDs, oversized fields, wrong types) as defense in
depth, not as the only line of defense.

## Strict parser

`parse_decision()` never raises for a malformed or unsafe model response -
it returns a typed `ParseSuccess`/`ParseFailure` (mirroring
`kernel/knowledge_base/answer.py`'s `parse_structured_answer()`
contract). It performs complete-response parsing only (no prose before or
after the JSON object survives), strips at most one whole-response
Markdown fence, rejects duplicate JSON keys and `NaN`/`Infinity`, rejects
JSON nesting deeper than 8, and never logs the raw model response text.

## No execution, no confirmation access, no production caller yet

This package imports no executor and no confirmation store - it cannot
run a tool and cannot grant, check, or bypass confirmation, no matter
what a model or a user's request text claims. Nothing in
`kernel/orchestrator/`, any `capabilities/`, or `interfaces/whatsapp/`
calls this package yet. That wiring, along with persisted task state
(Milestone 40), a bounded planner (Milestone 41), and an autonomous
execution loop (Milestone 42), is explicitly out of scope here.

## Known limitation: conservative grammar, intentional false negatives

Stage A's recognizers are deliberately narrow - "favor false negatives
over false positives." A legitimately-intended request phrased outside
the recognized forms falls through to a model call with zero candidates
(the model can then only `respond`, ask for clarification, or decline -
never select a tool it wasn't offered). Broader natural-language coverage
is a product tradeoff for a later milestone, not a defect to work around
here.
